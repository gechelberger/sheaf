# M9: Markup completion

Status: **in progress** (started 2026-10-14). Branch `m9`, cut from `main`
(which has all of M8). The decisions below were agreed at kickoff, when
Greg said to start.
One commit per slice; notes per slice at the end, as in M7 and M8.

## Scope

The roadmap's first cut, plus what planning turned up:

- **Infrastructure first** (slices 1–2, decided 2026-10-14):
  - **One sheaf process per user on each machine.** A second launch
    hands its files to the running sheaf; different users never share a
    process.
  - **Preferences split from state.** Preferences go in `settings.toml`,
    which you edit by hand. Remembered state goes in `state.json`, which
    is disposable.
  - **Edit history** (slice 4, added 2026-10-14). Every version keeps the
    commands that made it, and a History panel jumps to any version. It's
    also groundwork for merging conflicting edits later
    ([`file-contention.md`](file-contention.md)).
- **Folded in from Pending** (the PDFlyer parity gaps that are markup):
  - connector groups;
  - Set Status, which replaces "sign-off / review stamps";
  - Stamp Summary and Note Summary, as comment-panel filters and the
    summary export;
  - Recent and Favorite stamps, and user stamps shared across staff;
  - the PDFlyer tape: sections and row numbers, editing a placed tape,
    rotating and resizing it.
- **Added, because the planned items need them:**
  - **Editing placed marks.** Today no mark can be resized or recolored
    once placed. Polygons, callouts, stamps and tapes all need handles.
  - **Text selection and Copy.** sheaf can't select or copy page text at
    all. Underline, strikethrough and replace-text want a run of text,
    not a rectangle.
  - **An identity** (name and initials) for authors and dynamic stamps.
    Today the author is `$USER`, with no way to change it.
- **Dropped:** "Sign-off / review stamps" as a feature of its own.
  Dynamic stamp presets ("Reviewed GE 10/14/26") and Set Status cover it.
  PDFlyer has no sign-off. Engagement-style sign-off (binder-level,
  preparer then reviewers) stays plugin work, per Not planned.
- **Cut line:** measurement (slice 19) is the least used by tax and audit
  staff. If M9 runs long, it moves to a later milestone without holding
  up v0.5.

## Found while planning

Bugs and gaps in today's code. Slices 1–2 fix 9–11, slice 3 fixes 1–5
and 12, slice 4 fixes 13, and the slice in brackets fixes the rest.

1. **Marks are lost when pages come from another file.** Insert Pages >
   From File… and Replace Pages never read the inserted file's sheaf
   marks into the model (`DocView::insert_file`). PDFium draws them, since
   only the primary file's marks are hidden, so they look fine until a
   save strips them as stale (`build_rewrite` and the incremental path
   both call `strip_sheaf_annots` on pages with no model marks).
   `sheaf combine` does import them (`sheaf_ops::combine`).
2. **Bookmark colors aren't read on open.** `OutlineItem` has no color
   (`sheaf-render/src/lib.rs`), and loaded bookmarks get `color: None`
   (`outline_from_flat` in `model.rs`). So colors, sheaf's or PDFlyer's,
   vanish on reopen, and any outline rewrite drops them: Save As, or an
   incremental save after a bookmark edit, including a page delete that
   removes one.
3. **An older sheaf deletes marks it can't read.** A `/SheafAnnot` whose
   JSON doesn't parse is skipped (`file::annots_in`) and then stripped on
   save, since stripping matches any `/SheafAnnot`. Once M9 adds kinds, a
   colleague on an older build would silently delete them.
4. **The third-party comment list goes stale.** It's read only at open
   (`foreign_annots` in `docview.rs`). After a save that renumbers pages
   it points at the wrong pages, and comments on inserted pages never
   appear.
5. **Replace Pages leaves orphaned marks.** It removes the leftover old
   pages but not their entries in `DocState::annots`.
6. **Acrobat replies to our marks break.** Every save writes our marks as
   new objects (`write_page_annots`), so a third-party reply's `/IRT` to
   one of them dangles. [Slice 8, by decision 4.]
7. **Highlight ignores unsaved OCR text.** It asks PDFium for glyph boxes
   (`highlight_from_drag`) and never `TextLayer::boxes_in_rect`. [Slice 6.]
8. **Links don't work in the page view.** Clicking a link does nothing;
   connectors jump only through sheaf's own code. Not markup, so it's a
   new Pending entry.
9. **Windows overwrite each other's settings.** Each window loads
   `settings.json` once (`Launch::settings`) and saves its whole copy
   after any dialog or layout change. Window B is open; you print from
   window A with new choices; then you toggle a dock in window B. B saves
   its stale copy, and A's print choices are gone from disk. A hand edit
   made while sheaf runs is overwritten the same way. A file with a typo
   is read as defaults, and the next save writes those over it. [Slice 2.]
10. **Pattern presets are lost across windows** the same way. Each
    Patterns panel loads its own list and saves the whole list
    (`pattern_panel.rs`). [Slice 2.]
11. **Two sheaf processes can open the same PDF.** Within one process, a
    file that's already open just brings its window forward, because "two
    views of one file would share a recovery sidecar and each save would
    discard the other's edits" (`open_paths` in `workspace.rs`). But each
    launch from the file manager is a new process, and nothing checks
    across processes. [Slice 1, for one user's processes. Two people, or
    sheaf and Acrobat, on one file is deferred:
    [`file-contention.md`](file-contention.md).]
12. **Mark ids collide across copies of a file.** Ids are the highest so
    far plus one (`next_annot`), so two copies of a binder give different
    marks the same `/NM`. Replies (slice 8) and importing a reviewer's
    comments from their copy (slice 18) match by `/NM`, and would attach
    to or overwrite the wrong mark. [Slice 3.]
13. **Undo past a save, then save, writes the wrong pages.** Reproduced
    2026-10-14 with a throwaway test following the app's steps.
    - **Why:** the model doesn't hold page content. A page is
      `(source, index, rotation)`, and a source is a path. The screen
      reads each source from the bytes PDFium loaded when it was opened,
      but a save re-reads every source from its path (`file::load_pdf`,
      `incremental::build`).
    - **The steps:**
      1. Open a three-page file: A0 A1 A2.
      2. Move A2 to the front, and Save. The file on disk is now
         A2 A0 A1.
      3. Undo. The model is back to source 0's pages 0, 1, 2, and the
         screen shows A0 A1 A2.
      4. Save. The file is still A2 A0 A1, whether the first save was
         incremental or a full rewrite. Source 0's path now holds the
         saved file, so its "page 0" is A2.
    - **In the app,** reopening after that save brings back the wrong
      order. Marks and bookmarks, which follow page ids, end up on the
      wrong page content. Rotations already written into the file would
      be applied twice.

    A History panel that jumps across saves makes this easy to hit.
    [Slice 4.]

## Decided at kickoff (2026-10-14)

1. **The `/SheafAnnot` JSON is a file format.**
   - Changes are additive: a new kind is a new variant, a new field has
     `#[serde(default)]`, nothing is renamed.
   - A mark this build can't read is kept as a third-party mark, not
     stripped (bug 3).
   - Every mark still writes a full `/AP`, so Acrobat and older sheaf
     builds draw it.
2. **One mark can write several objects.** `annot::to_pdf` returns the
   annotation plus extra objects: a stamp's Form XObject, the Caret half
   of a replace-text edit, an attachment's embedded file. Slice 3 changes
   the signature; later slices use it.
3. **Identity and dates.**
   - A name and initials in `settings.toml` (`[identity]`, with `name` and
     `initials`), with no dialog (decision 14). The name defaults to the
     OS user and the initials to the name's. They're the author of new
     marks, replies and status changes, and they fill in dynamic stamps.
   - Marks gain a creation date (`/CreationDate`) that moving or editing
     doesn't change. PDFlyer's Stamp Summary shows when a stamp was
     applied; today `modified` is all there is, and a move overwrites it.
4. **Replies and review states are standard annotations, threaded by
   `/NM`.**
   - In the file they're what Acrobat writes. A reply is a Text
     annotation with `/IRT` to its parent. A status is a hidden Text
     annotation with `/IRT`, `/State` and `/StateModel`: Review (None,
     Accepted, Rejected, Cancelled, Completed) or Marked (the checkmark).
   - In the model they point at their parent's `/NM`, either sheaf's
     (`sheaf:<id>`) or a third-party one. `/IRT` object references are
     resolved at save, which also re-points Acrobat replies to our marks
     (bug 6). A third-party comment without `/NM` gets one when it's first
     replied to.
5. **Third-party comments become workable, in two steps.**
   - Slices 8–9: they can be replied to, given a status or checkmark,
     filtered, hidden and deleted.
   - Slice 18: editing one (moving it, resizing it, changing its text or
     color) turns it into a sheaf mark when its subtype maps onto a sheaf
     kind. The converter is the same one FDF/XFDF import uses.
6. **Custom stamps are one-page PDFs.**
   - Adding an image stamp converts it to a one-page PDF
     (`sheaf_doc::images`), so image stamps and PDF-page stamps share one
     path.
   - The library is a folder of stamp PDFs in the config directory, one
     stamp per page, the way Acrobat keeps its Stamps folder. Sharing
     with staff means sending that PDF (PDFlyer's Export/Import).
   - In a document, a stamp's appearance is its page as a Form XObject.
     The model names it by content hash in the generated-file cache (M8's
     "generated pages are files"). On a machine without that file, it's
     recovered from the saved `/AP`.
7. **Dynamic stamps are filled in when placed.** Tokens (`<<name>>`,
   `<<initials>>`, `<<date>>`, `<<time>>`) are resolved at placement and
   then fixed. That's how an Acrobat dynamic stamp looks to everyone after
   it's placed. No JavaScript.
8. **Connectors are label groups.**
   - Every connector with the same label is one group, as in PDFlyer.
     Previous/Next and "pages with / without this label" navigate it.
   - Labels are 1–50 and A–ZZ, chosen from a picker that defaults to the
     next unused label.
   - Each connector's `/Dest` points at the next one in page order,
     wrapping, so clicking walks the group in Acrobat too.
   - Today's pairs are groups of two (every pair has its own number), so
     existing files keep working. Deleting one connector no longer deletes
     its partner.
9. **Measurements are standard dimension annotations.** They're Line,
   PolyLine and Polygon with `/IT` set to `/LineDimension`,
   `/PolyLineDimension` or `/PolygonDimension`, and a `/Measure`
   dictionary, so Acrobat reads them as measurements. Snapping to page
   geometry waits for vector extraction
   ([rust-ecosystem.md](../docs/prior-art/rust-ecosystem.md), shared with
   the table finder). Snapping to M7's grid and guides is in.
10. **Comment operations go in `sheaf-ops`,** with a `sheaf comments`
    subcommand (export, import, summary), per the ops/CLI rule. M15's
    batch actions chain them.
11. **Generated text stays Helvetica/WinAnsi.** Characters outside
    WinAnsi print as `?`, as in marks, headers and footers today, and the
    comment summary inherits that. Unicode output (embedding a font,
    perhaps through krilla) is a separate decision that M10 will force for
    form appearances.
12. **One plugin API bump, at the end.** New kinds and fields can't be
    added to WIT 0.2 compatibly ([plugins.md](../docs/plugins.md),
    versioning). Until slice 20, `annotations()` leaves the new kinds out
    for 0.2 plugins. Slice 20 adds a 0.3 world with all of them and keeps
    serving 0.2.
13. **Keys.** Acrobat's first, Foxit's where Acrobat has none. All are
    free today:

    | Key | Does | From |
    |---|---|---|
    | Shift+U | cycle Highlight, Underline, Strikethrough, Squiggly | Acrobat |
    | E | Text Edits: replace selected text, or insert at a click | Foxit |
    | Shift+D | cycle the drawing tools | Acrobat |
    | Q | Cloud | Acrobat, Foxit |
    | X | Text box (T stays); Shift+X cycles text box and callout | Acrobat |
    | J | Stamp (K stays Tickmark); Shift+J cycles Stamp and Attach File | Acrobat, Foxit |
    | Shift+K | checkmark the selected comment | Acrobat |
    | R in the Comments panel | reply (R on the page stays Rotate) | Acrobat |
    | Ctrl+Enter | send a reply | Foxit |
    | Ctrl+C, Ctrl+V, Ctrl+Alt+V | copy text or marks; paste; paste in place | Foxit |
14. **Preferences and state are separate files, with no settings view
    yet.** Decided by Greg, 2026-10-14.
    - **`settings.toml`** holds preferences: identity, stamp size and the
      like. You edit it by hand, and sheaf only reads it. Its mistakes
      can't cost you anything else.
    - **`state.json`** holds what sheaf remembers: window placement,
      docks, last-used dialog choices. sheaf writes it, and it's
      disposable. If it breaks, delete it, and no preference is lost.
    - It's TOML (decided 2026-10-14). TOML allows comments and has no
      trailing-comma errors, and sheaf can create the file with every
      setting commented out and explained. Plugin manifests are TOML
      already. The settings view, when it comes, can write it with
      `toml_edit`, which keeps the comments.
15. **One sheaf process per user on each machine.** Decided by Greg,
    2026-10-14. That process holds a lock, owns `state.json`, and opens
    every window. A second launch hands its files to it and exits. So
    `state.json` has one writer by construction: no file lock around
    writes and no per-process temp names are needed. Different users
    never share a process.
16. **History and the edit log are one tree.** Asked for by Greg, and the
    shape confirmed, 2026-10-14.
    - **Nodes are versions:** a snapshot of the document plus a stable id,
      a label, the author (identity), the time, and the saves that wrote
      it.
    - **Edges are commands:** the edits that turned the parent into the
      child. Each node has one parent, so they're stored on the child
      (`Version { parent, edits, state, … }`).
      - An edge can hold several edits: a batch, or a job such as OCR
        whose later batches add to the same edge, as they amend the same
        version today.
      - The root has no edge. It's the file as opened; loading its marks
        and labels builds it.
    - **Undo, redo and jumps move a cursor** between nodes. They never
      make one. Commands only replay forwards, so they need no inverses.
    - **Edits are kept resolved,** with the ids they assigned (mark ids,
      new page ids) filled in. Replaying them on the same base then gives
      the same state. With random mark ids (slice 3), that's the only way
      to get the same ids twice.
    - **Each edge is self-contained.** Adding a source (Insert, Replace,
      generated pages) happens outside `Edit` today, through `add_source`.
      It becomes part of the edit that needs it, so the edges alone
      rebuild every version from the root.
    - **A save is a mark on a node, not an edge.** After a save, the
      current node's pages are re-pointed at the saved file
      (`rebase_to_saved`), so the next incremental save is computed
      against it. The content is the same, so that re-expresses the node
      in place. It isn't a step you can undo.
    - **Branches are kept.** Today an edit after undo throws away
      everything after the cursor. Instead it starts a branch, and the old
      one stays reachable. Redo follows the branch you were last on.
    - **Snapshots are a cache over the commands.** Trimming (200 versions
      or 256 MB, as now) drops snapshots: abandoned branches first, then
      the oldest. Their edges stay, at least back to the last save, so a
      future merge can replay them. Jumping to a node whose snapshot is
      gone replays forward from the nearest one that's kept, as long as
      the sources it needs are still held.
    - **Only for the session,** for now. Keeping the log across sessions
      is a later decision. It could let crash recovery restore undo, or
      give an audit trail of who changed a binder. Stored inside the PDF,
      it would carry deleted text, so M11's sanitize would have to strip
      it.

## Slices

1. **Single instance** (decision 15; bug 11).
   - **Who owns:** an OS file lock (`std::fs::File::try_lock`) on
     `instance.lock` in a local, per-user runtime folder:
     `$XDG_RUNTIME_DIR/sheaf` on Linux, `%LOCALAPPDATA%\sheaf\run` on
     Windows, `$TMPDIR/sheaf` on macOS.
     - Never the config folder. On Windows that's `%APPDATA%`, the
       *Roaming* folder, which firms with roaming profiles or folder
       redirection keep on a network share. Sockets don't work there, and
       a lock there would span machines: the same user signed in at a
       desktop and in an RDS session would be locked out of one.
     - The OS releases the lock when the process ends, crash included, so
       there's never a stale lock to clean up.
     - One instance per user on each machine, so one per user on a
       terminal server (accounting firms on RDS or Citrix). A scratch
       `SHEAF_CONFIG_DIR` (tests, the screenshot harness) moves the
       runtime folder under it, so it still gets its own instance.
   - **Talking to it:** a local socket beside the lock.
     - Unix domain sockets work on Linux, macOS and Windows 10 1803+ (via
       `uds_windows`, already in the dependency tree). In a per-user
       folder, the socket is per-user by its file permissions. A Windows
       named pipe, by contrast, has a machine-wide name that would need
       the user folded into it.
     - Socket paths are limited to about 104–108 bytes, so a long config
       path falls back to a short hashed name in the runtime or temp
       directory.
     - The listener has its own thread and answers at once, then hands the
       request to the main thread, so a busy window doesn't make the
       launcher wait.
   - **A second launch** of `sheaf [files…]`:
     1. fails to take the lock;
     2. connects and sends one JSON line: protocol version, the files
        (made absolute against the launcher's working directory) and an
        activation token;
     3. waits a few seconds for the reply, then exits.

     Edge cases:
     - The socket may not exist yet: a file manager can start one
       process per selected file, all at once. The owner binds the socket
       before GPUI starts, and launchers retry briefly.
     - The owner may be quitting: the launcher tries the lock again.
     - An owner that never answers gets an error ("sheaf is running but
       not responding"), not a second instance.
   - **Never hands off:**
     - the subcommands, which are headless processes of their own and
       only read `settings.toml`;
     - `--script` and `--selftest-*`;
     - `--new-instance`;
     - debug builds, unless `SHEAF_SINGLE_INSTANCE=1`, so `cargo run`
       doesn't hand files to the installed sheaf.

     An instance without the lock writes nothing in the config
     directory: no state, no recent files.
   - **Opening what's handed over:**
     - through today's open-or-focus (`open_paths`, `same_file`);
     - passwords aren't forwarded; the owner prompts;
     - the window comes forward. That needs Wayland's
       `XDG_ACTIVATION_TOKEN` passed along, and on Windows the launcher
       allowing the owner to take the foreground; otherwise the window can
       open behind others.
     - On macOS, Finder opens arrive through GPUI's `on_open_urls`. Wire
       that to the same path.
   - **Check on Windows:** `same_file` with a mapped drive against its
     UNC path (`S:\…` vs `\\server\share\…`). Firms keep binders on file
     servers.
   - **Checks:**
     - two launches at once give two windows in one process;
     - launching a file that's already open brings it forward;
     - after `kill -9` of the owner, the next launch takes over;
     - a scratch config directory is independent.
2. **Preferences and state** (decision 14; bugs 9–10).
   - **`settings.toml`:**
     - Read at start, and again when a window gains focus and the file
       has changed.
     - Each key is parsed on its own, so a bad value falls back alone.
       The error (key, line, column) shows as a notice, and unknown keys
       get a warning (likely typos).
     - Edit > Open Settings File opens it in the system's editor
       (`open_with_system`, from the attachments panel). If there's no
       file yet, it first creates one with every setting commented out
       and explained.
     - The preference types live outside the app (in `sheaf-ops`), so
       the CLI reads identity too.
     - First entries: `[identity]`. Later slices add theirs (stamp size
       in slice 10).
   - **`state.json`:**
     - Holds window placement, docks, and the last-used choices for
       print, scan, combine, blanks and OCR.
     - Today's `settings.json` holds only these, so it's renamed on first
       run.
     - If it doesn't parse, it's moved aside to `state.json.bad` and sheaf
       starts fresh.
   - **In memory:** one GPUI global holding `Arc<Prefs>` and
     `Arc<State>`.
     - Commands and background jobs take an `Arc` when they start and
       keep it for the run. Today the plugin OCR call re-reads the file on
       every call; it takes the snapshot instead.
     - Changes go through `update(cx, |state| …)`, which applies to the
       current value, never to a window's old copy (bug 9).
     - Window and dock state only set the default for new windows; open
       windows don't move. A preference change reaches every window.
   - **Writes:**
     - batched (about 500 ms), through one writer task;
     - written to a temp file then renamed (`tempfile`), with stray temps
       cleared at start;
     - flushed once more on quit.
   - **Patterns and toolbar:** `patterns.json` becomes one shared list
     (bug 10). It and `toolbar.json`, which both sheaf and you write, get
     the same reload-on-change.
   - **Checks:**
     - a dock toggle in one window doesn't undo another window's print
       choices;
     - a typo in `settings.toml` leaves every other setting working and
       shows the error;
     - a corrupt `state.json` gives a fresh start;
     - a job started before a change keeps its snapshot.
3. **Groundwork, and bugs 1–5.**
   - **The mark record:**
     - serde defaults;
     - ids unique across copies of a file (random 64-bit, not highest
       plus one), so `/NM` names one mark everywhere (bug 12); old
       numbered ids still read;
     - the creation date;
     - identity from `settings.toml`;
     - `to_pdf` returning extra objects;
     - unreadable marks kept rather than stripped.
   - **Marks from other files:**
     - Insert Pages and Replace Pages import the file's marks in the same
       undo step.
     - Replace Pages drops the marks of the pages it removes.
     - The third-party list is re-read after a save or an insert.
   - **Bookmarks:** `/C` and the style flags `/F` (bold, italic) are read
     on open and kept through rewrites. The model gains the style, which
     Set Status uses.
   - **Checks:**
     - a mark with an unknown kind survives a save;
     - a marked file inserted, saved and reopened keeps its marks;
     - bookmark colors round-trip by both save strategies.
4. **Edit history** (decision 16; bug 13).
   - **The model** (`sheaf-doc`, `model.rs` and `history.rs`):
     - versions with ids and parents, so history is a tree;
     - `compute` returns the resolved edit alongside the new state;
     - `add_source` folded into the edits that need it;
     - saves recorded on the node they wrote;
     - trimming, and jumps that replay from the nearest kept snapshot, by
       decision 16.
   - **A source is the bytes read when it was opened, not a path** (bug
     13).
     - Each source keeps its bytes (`Arc<[u8]>`), read once when it's
       opened, and saves build from them. Nothing re-reads a source's path
       after that. The path is kept for display, for reopening, and as
       Save's default destination.
     - Then what's on disk no longer matters until a file is opened again,
       which is what the in-memory model was meant to guarantee.
     - PDFium already holds a copy of each source's bytes for as long as
       sheaf runs. Ideally the model and the renderer share one buffer, so
       the change costs no extra memory.
     - History trimming can then free a source's bytes once no kept
       version refers to it. That's also the start of cleaning up the
       generated-file cache.
     - Check: the reproduction above, as a regression test, by both save
       strategies.
   - **History panel** (View > Panels > History, Ctrl+Alt+8):
     - the versions on the current line, oldest first: label, author and
       time;
     - the current version marked, the saved one flagged, undone ones
       dimmed;
     - click a row (or use the arrows and Enter) to jump there;
     - a branch point shows the edits that were undone and replaced, and
       you can jump into them;
     - expand a row to see its commands in words ("Delete pages 4–6",
       "Highlight on p. 3"), from a description for each `Edit` variant;
     - virtualized, for long sessions.
   - **A jump moves the cursor, like undo.** It isn't an edit, so jumping
     back and forth is free, and Save writes whichever version is current.
     A running job (OCR) ends its undo step when you jump away, as it
     does today when you edit.
   - **Later slices:** every one that adds an `Edit` variant adds its
     description.
   - **Checks:**
     - jump back ten versions and forward again;
     - an edit after undo leaves the old branch reachable;
     - a property test: replaying the log from the base reproduces every
       version's state, over random edit sequences;
     - undo past a save, then save, writes the right pages, by both save
       strategies.
5. **Editing placed marks.**
   - **Handles:** corners and edges for box marks (shapes, text boxes,
     stamps, tapes), and endpoints for lines. Shift keeps the aspect
     ratio, or 45° for lines.
   - **Hit-testing by shape** for lines and ink, not by bounding box.
   - **A properties bar** for the selection: color, fill (`/IC`) for
     rectangles and ellipses, opacity, line width, dashes, arrowheads at
     either end, text size. Each change is one undo step.
   - **Multi-select:** Shift+click adds to the selection. Move, delete,
     copy and the properties bar act on all of it.
   - **Text on the page:** double-click a mark to edit its text. Today
     that's only possible from the Comments panel.
   - **Copy and paste** marks (Ctrl+C, Ctrl+V), paste in place
     (Ctrl+Alt+V), across documents too.
   - **Ctrl+drag** moves a mark under any tool: PDFlyer's way of moving
     stamps without leaving the stamp tool.
6. **Text selection and Copy.**
   - The Select tool (V) selects text when a drag starts on text, and
     marks when it starts on a mark, as in Acrobat.
   - A selection is a run in reading order: PDFium's character order, or
     the OCR layer's, so unsaved OCR text works (bug 7).
   - Ctrl+C copies the selected text.
   - The text markup tools act on the current selection when there is
     one: select, then press U. That's Acrobat's quick actions.
   - Build it so M13's text editing can reuse the character-level
     selection.
7. **Text markup and text edits.**
   - **Underline, strikethrough, squiggly:** QuadPoints over a selection
     or a drag, like Highlight. Shift+U cycles them.
   - **Text Edits (E):**

1. Done. A new crate, `sheaf-instance` (no GPUI, so it type-checks for
   Windows: `cargo clippy -p sheaf-instance --target
   x86_64-pc-windows-msvc`), and `crates/sheaf-app/src/instance.rs`.
   - **Owner:** `try_lock` on `instance.lock` (it holds the owner's pid),
     then a socket. A socket path too long for an address (over 100 bytes)
     falls back to `<temp>/sheaf-<hash>.sock`; the scratch config the
     tests use hits that.
   - **Requests:** one JSON line with the protocol version, absolute paths
     and the activation token. The reply is `ok`, `retry` (the owner is
     quitting, or its app stopped listening) or a refusal (another
     protocol version).
   - **Opening:** the owner opens handed-over files through
     `workspace::open_from_launch`: an open file comes forward, then an
     empty window fills, then new windows. With no files, the frontmost
     window comes forward.
   - **Safety:** on Unix the runtime folder must be ours, not a symlink,
     and not writable by others, and both ends of the socket check the
     peer is the same user (`SO_PEERCRED`, `getpeereid`).
   - **Quitting:** quitting stops the owner first (`instance::quit`, at
     all three quit sites), so launches wait for the lock instead.
   - **macOS:** Finder's opens arrive as file URLs through
     `on_open_urls` and go down the same path. Untested.
   - **Not the owner:** a process that isn't the owner writes no
     `settings.json` and no `recent.json` (`instance::owns_state`). Slice
     2 reworks those files; patterns, toolbar and plugin changes are
     explicit and still saved.

   Deviations from the plan:
   - **An owner that never answers** (3 s) leaves the launch running
     alone, writing no state, with a line on stderr, rather than showing
     an error. An error needs a window anyway, and running alone is safe
     for state. The listener answers from its own thread, so this means a
     wedged process, not a busy one.
   - **The dev flags** (`--timing`, `--find`, `--panel`, `--pattern`,
     `--menu`, `--password`, `--script`, `--selftest-*`) can't be handed
     over, so they imply `--new-instance`.
   - **Wayland:** GPUI asks for its own activation token when it activates
     a window, and the compositor usually refuses, so a handed-over window
     may not come to the front (Mutter flags the app instead). The
     launcher's token is sent for when GPUI can use it.
   - **Sessions:** one owner per user on each machine, not per session. A
     second graphical session of the same user on one machine would hand
     its files to the first session's sheaf.

   - **History is a tree** (decision 16), in `model.rs`.
     - A `Version` has a parent, children and a `redo_to`, plus its
       label, author, time, `Step`s, the sources registered since its
       parent, an optional snapshot, and its saves.
     - Undo goes to the parent; redo follows `redo_to`; `jump` goes
       anywhere and points the `redo_to`s along the way at it. An edit
       after undo makes a branch instead of discarding.
   - **Replay.** A `Step` is an edit plus the id counters it started from
     and the seed of its mark-id RNG (`Document::rng`, reseeded per step).
     So replaying a version's steps on its parent's state gives exactly
     its state, ids included. `ensure_state` replays from the nearest
     ancestor with a snapshot.
   - **Trimming:**
     - It drops snapshots, not versions: those off the current line
       first, then the line's, oldest first.
     - Never the opened version's, the current one's, or any saved
       one's. A save re-expresses its version in place, so it can't be
       replayed into.
     - The policies (`FixedCount`, `MemoryBudget`) keep their meaning,
       counted in snapshots.
     - Versions themselves are kept up to `history::MAX_VERSIONS`
       (1000). Past that, leaves of other branches go first, then the
       root moves forward, but never past the saved version.
   - **Saves** are marks on a version (`Saved`), not edits;
     `rebase_to_saved` registers the saved file without logging it.
   - **The edge into a version** (its steps and sources) is what a merge
     would replay: `Document::edge`.
   - **`describe.rs`** puts each edit in words ("Delete pages 4–6",
     "Add a highlight on page 3"). Page numbers come from the parent's
     snapshot when it's kept; otherwise counts.
   - **History panel** (`history_panel.rs`; View > Panels > History,
     Ctrl+Alt+8; in the right dock by default):
     - one row per version: label; author and local time (chrono, already
       in the tree); "Saved"; the current version highlighted; undone
