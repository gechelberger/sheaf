## Scope

The roadmap's first cut, plus what planning turned up:

- **Fill** AcroForms: text (comb, multiline, auto size), check boxes,
  radio buttons, combo and list boxes, and button actions. sheaf writes
  the appearance of every value it changes, so values look the same in
  every viewer.
- **Scripts:** a sandboxed subset of Acrobat form JavaScript in boa, run
  as a WebAssembly guest (decisions 1 and 3): the AF functions,
  keystroke, validate, calculate and format, and document-level
  functions. Not a general JS runtime.
- **Create and edit fields** (Prepare Form): every field type,
  properties, tab order, calculation order, alignment tools.
- **Form data** in and out: FDF, XFDF, CSV, tab-delimited text and JSON.
  Acrobat's XML moves to later.
- **Flatten form fields,** in Export Flattened Copy and as an edit.
- **XFA:** a clear notice for XFA-only forms. Hybrid forms (an AcroForm
  with an XFA copy beside it) are filled through the AcroForm.
- **Automatic field detection** on flat forms, born-digital and scanned.
- **Added, because the planned items need them:**
  - **A field model.** Today sheaf carries widgets through saves without
    reading them; nothing knows the field tree.
  - **Forms that survive page tools.** Crop, watermark and Remove
    Header/Footer destroy a page's form today, and Insert, Combine and
    Replace leave the incoming fields orphaned (bugs 1–5). Filling is
    wasted if the next page tool loses it.
  - **Save rules for hybrid XFA, usage rights and signed files** (bugs
    6–7), on every way out of the binder. Without them Acrobat shows the
    stale XFA copy instead of what sheaf filled, Reader's usage-rights
    signature no longer matches the file, and a save can break a
    signature without asking.
  - **A Unicode font for appearances, and an editor that matches
    them.** M9 decision 11 left the font to M10: today any character
    above U+00FF is written as `?`.
  - **A forms corpus and a form check** (slice 1), used by every later
    slice's tests.
  - **Field values in Find, Patterns and text export** (bug 8). M11's
    leak check searches form values too.
- **Reordered** (proposal 4): fill first, then flatten and data, then
  scripts, authoring and detection. The roadmap says IRS and state forms
  depend on calculations; none of the 29 IRS forms has a field script,
  and only Georgia's of the 11 state forms does real arithmetic. So IRS
  forms work fully before any JavaScript does.
- **Cut line:** field detection (slices 27–28). If M10 runs long, it
  moves to a later milestone without holding up v0.6.
- **Moved out:** signing and Fill & Sign to M12, batch filling and a
  copy per CSV row to M15, removing scripts when sanitizing to M11
  (proposal 22).

## Decided while planning (Greg, 2026-10-14)

1. **The form JavaScript engine is boa_engine.** The roadmap's "decide
   at kickoff: boa or QuickJS" is settled.
   - 0.22.0 is current (published 2026-08-28). It needs Rust 1.91;
     sheaf is on 1.98. It's licensed Unlicense OR MIT; 18 of its
     dependencies (ICU4X data) are Unicode-3.0.
   - It parsed all 477 distinct scripts in the corpus (66 ms in all),
     and ran every file's document-level and open-action scripts without
     an error against a stand-in for Acrobat's objects.
   - pdf.js's form-script library runs in it unchanged, natively and
     inside the wasm guest (proposal 12).
   - It runs as a WebAssembly guest (decision 3). What scripts may do is
     proposals 12–13.
2. **M10 comes before M11.** M11 was planned first, and ROADMAP.md
   still says "M10 is skipped for now" (ROADMAP.md:245, and
   [`m11.md`](m11.md) lines 3–4). That's changed: M10 is next.
   - At kickoff (or in slice 1), ROADMAP.md's M10 section gets the
     usual "Started …" line, loses its "Decide at kickoff" paragraph
     (ROADMAP.md:240), and its "Slices:" line (:237) takes this plan's
     order. "CSV/XML" (:232) becomes CSV, with XML later. M11's section
     and `m11.md` say it follows M10.
   - M11's plugin API bump (its proposal 15) becomes 0.5, since M10
     takes 0.4.
3. **boa runs as a WebAssembly guest in sheaf's wasmtime,** not in
   sheaf's process and not as a process of its own. Greg had assumed it
   would need a sandbox and pictured a separate process, but "a wasm
   sandbox is much cleaner and for the scale of scripts that I expect us
   to deal with the performance should not be an issue".
   - **In-process boa can't be made safe against a hostile PDF.** In
     the spike, on an 8 MiB stack:
     - about 330 bytes of `(`, closed or not, crash the process: boa's
       parser overflows the stack between 300 and 330 levels, and
       upstream issues #4397 and #4311 are open;
     - `JSON.stringify` of an object nested 20,000 deep aborts too;
     - a backtracking regex (`/(a+)+$/` on 28 characters) ran 20.4 s,
       and `new Array(1e8).join(…)` peaked at 7.07 GB, each inside one
       built-in call that nothing can stop;
     - there's no memory limit, and a failed allocation aborts;
     - boa has no interrupt API (#3442, open since 2023). Its loop limit
       is per call frame: 100 calls of about a million iterations each
       ran under a limit of a million. Callbacks from built-ins aren't
       counted: a nested `forEach` ran 42.6 s. Its async budget doesn't
       reach built-in callbacks, and through pdf.js's `eval` path a
       250 ms deadline was ignored (the script ran 7.2 s).
   - **In wasmtime every one of those trapped,** and the host ran on:
     the same boa built for wasm32-wasip2 (with `annex-b` alone) and run
     by wasmtime 49.0.2, the version `sheaf-plugin` uses, with an epoch
     deadline, a memory cap and a 64 MiB wasm stack. A fresh instance
     then ran normally.
     - The second spike ran them again on the build sheaf would ship
       (`annex-b` and `xsum`, pdf.js loaded), with a 1 s deadline and a
       256 MiB cap. Up to 4,000 nested parentheses parse (557 ms). From
       5,000 the 64 MiB stack overflows (about 14 KiB a level), which
       traps cleanly because the stack comes first in the guest's
       memory.
     - Endless loops (inside `try` too), the backtracking regex, the
       nested `forEach`, a 20,000-deep `JSON.stringify`, and
       `while(true){}` as a field's Validate action through pdf.js's
       `eval`, all trapped at about 1,065 ms (the ticker's drift).
     - `new Array(1e8).join` and string doubling were refused memory at
       the cap (196.9 MiB) and trapped, with the allocation failure in
       the captured stderr. `f(){f()}` hit boa's recursion limit, an
       error scripts can catch.
     - A store that trapped refuses to run again
       (`CannotEnterComponent`), so it's dropped. A fresh one then
       committed normally every time.
   - **The cost is about 2x** (boa alone here; with pdf.js, 1.5–2x,
     proposal 12):

     | | Native | wasm |
     |---|---|---|
     | Context, form objects and AF library | 0.74 ms | 1.10 ms |
     | A SUM calculation, called as a function | 39 µs | 78 µs |
     | `AFNumber_Format` | 28 µs | 58 µs |
     | 500 calculations in one cascade | 5.2 ms | 11.0 ms |

     With pdf.js in it, compiling the guest takes 0.44 s on 32 threads
     and 6.9 s on one. The compiled form (16.9 MB) is cached and loads
     in 0.4 ms with `deserialize_file` (mmap), or about 11 ms from
     bytes. An instance takes 0.03 ms (0.15 ms the first).
     - Compiling inside sheaf's process leaves a 280–305 MB high-water
       mark from Cranelift, so it happens once, off the UI thread, and
       the cache is what normally loads. From the cache, the spike's
       host process started at 8 MB and peaked at 39.5 MB through
       Ohio's form.
   - **It also keeps boa out of sheaf's build.** Natively, boa adds
     8.0 MB to the binary, 131 crates (37 not in the lock) and 141 s to
     a clean release build, 91 s of it in `boa_engine`. As a guest with
     pdf.js it's a 6.64 MB `.wasm` (1.75 MB gzipped), built in its own
     workspace like the bundled plugins: 119–124 s clean, mostly
     `boa_engine`, and 34–38 s after a change to the guest's own code.
     It's built as a `cdylib` only, as measured; adding `rlib` changes
     what thin LTO produces.
   - **The guest gets almost nothing.** The spike's guest imports
     sheaf's own `sheaf:formjs/host` (the time zone, below) and 17 WASI
     0.2.9 interfaces: `io` poll, error and streams; `clocks`
     monotonic-clock and wall-clock; `random` random and insecure-seed;
     and `cli` stdout, stderr, stdin, environment, exit,
     terminal-input, terminal-output, terminal-stdin, terminal-stdout
     and terminal-stderr. No filesystem, sockets or `wasi:http`.
     - **Real, because they're called:** the wall clock (`Date`); the
       monotonic clock (boa's clock reads it as a context is built; a
       custom boa `Clock` would drop it); insecure-seed (hash seeding
       at load); random (`Math.random`); stdout and stderr through io
       streams, captured into 64 KiB memory pipes and sent to the script
       log, written only for a panic or out-of-memory message.
     - **Real but empty:** the environment, read only on that panic
       path, for `RUST_BACKTRACE`. Trapping it loses the message.
     - **Real though unused:** io poll and error, whose resource types
       the clocks and streams share.
     - **Trap stubs, never called:** stdin, exit and the five
       `terminal-*` interfaces.
     - The `WasiCtx` has no preopened folder, environment or arguments,
       and TCP, UDP and name lookup are off. Everything in the spike ran
       in it.
     - The plugin host isn't copied: its `wasi_ctx` inherits stderr and
       preopens granted folders (runtime.rs:561-581), and its linker
       adds `wasi:http` (runtime.rs:258-259).
     - **Not `Linker::define_unknown_imports_as_traps`** after
       wasmtime-wasi's `add_to_linker`. wasmtime-wasi 49 registers WASI
       0.2.12 and the guest imports 0.2.9, so the stubs' exact 0.2.9
       names shadow the version-compatible match, and every WASI call
       traps. Stubs are per interface, each resource defined only in
       the interface that owns it.
     - A test checks that the guest's import list equals this list.
   - **Threads:** one forms worker thread (a 128 MiB stack, reserved
     rather than committed) holds a wasmtime store for each document
     that has scripts. The UI sends events and gets back resolved
     changes; it never runs JavaScript.
     - **Set up at open, run at first use.** When a document with
       scripts opens, the worker loads pdf.js and sets up its sandbox
       from the field model in the background: 0.1–0.3 s in the guest,
       and no form JavaScript runs. The document's own scripts start at
       the first interaction (proposal 13). Set up at first focus
       instead, it would stall that focus 0.1–0.3 s.
     - A keystroke waits for its answer up to a short limit (in the
       guest a keystroke takes 0.25 ms, and a commit with five sums
       about 6 ms). Past the limit the key goes through, and the
       commit's own check decides.
     - A commit and its calculations run without blocking the UI and
       land as one edit. What happens when the user acts first is
       proposal 9.
     - A host call that waits for the user (a dialog) pushes the
       deadline back, as plugin calls do (runtime.rs:495-505).
     - **The sandbox follows the model.** pdf.js keeps its own copy of
       every field's value and properties. After any edit that changes
       them without coming from the sandbox (undo, redo, a History jump,
       an import, Clear Form, a plugin fill, a page tool, a rename, a
       Prepare Form edit), the host sends `sync {values, props}`. When
       the field tree changes, the store is rebuilt from the model's
       values.
     - **Idle stores go.** Linear memory never shrinks and a store may
       grow to the cap, so ten open binders could hold gigabytes. (The
       measured forms peaked at 65–77 MiB, nearly all of it the mostly
       untouched stack.) A store idle for 5 minutes, or beyond 4 live,
       is dropped. A store past 128 MiB is rebuilt. A dropped store is
       rebuilt from the model's values in the background when its
       window gains focus; an interaction that beats the rebuild waits
       for it (0.1–0.3 s, plus up to 70 ms of document scripts).
   - **Limits:** an epoch deadline of about 250 ms per keystroke and
     1 s per commit with its calculations; 256 MiB of memory; a 64 MiB
     wasm stack, with the guest linked for a 64 MiB stack (Rust's
     default 1 MiB traps at 100 nested parentheses). boa's own limits
     stay as a backstop: recursion 512, and a loop limit set from the
     corpus.
     - The 256 MiB includes the 64 MiB stack, so scripts get about
       192 MiB of heap.
     - The worker runs the guest synchronously on its 128 MiB thread.
       Deadlines are wall-clock, checked in the epoch callback as the
       plugin host does (runtime.rs:495-505); a ticker thread only
       advances the epoch every 1 ms so the checks happen. (The spike's
       ticker alone drifted 6.5%: a 1 s deadline trapped at 1,065 ms.)
     - In the spike the slowest steady commit was about 100 ms (a
       synthetic 300-field cascade), and Ohio's real one 70 ms. So the
       deadlines leave room, once pdf.js's slow first commit is patched
       (proposal 12).
   - **After a trap,** the instance is dropped and made again with the
     model's values, and a notice says "Form scripts stopped: took
     longer than 1 s". After three in one document, its scripts stay off
     until it's reopened.
   - **Features:** `default-features = false`, with `annex-b` (old
     scripts use `substr` and `escape`) and `xsum` (pdf.js needs
     `Math.sumPrecise`, aform.js:357). No `intl` (+16 MB), no
     `temporal`, and never `fuzz` (it gives `Context::default()` a
     budget of zero). boa supports only its latest 0.x release, so
     sheaf keeps up with its releases.
     - The second spike built this set (`annex-b` and `xsum`, without
       `temporal` or `float16`) with pdf.js. pdf.js loaded unchanged,
       and `Map.prototype.getOrInsertComputed`, which it uses, is there.
       `Math.sumPrecise` gives exact sums: `[0.1,0.2,0.3]` gives 0.6,
       and `[1e20,0.1,-1e20]` gives 0.1. The guest's size above and the
       timings in proposal 12 are for this set; the table above is boa
       alone with `annex-b`.
   - **Under wasm the local time zone is UTC,** so the host supplies the
     offset. The guest's `HostHooks::local_timezone_offset_seconds`
     calls a host import, `local-offset(unix-seconds) -> s32`, backed
     by `chrono::Local`.
     - Checked in the spike under Los Angeles, New York, Kolkata
       (`getTimezoneOffset()` -330), Lord Howe (a half-hour DST shift:
       -660 in January, -630 in July) and UTC. `printd` and `scand`
       follow it.
     - Without it, boa falls back to the `time` crate, which gives UTC
       under wasm.
     - A date expression calls the host a few times (about 15 calls for
       6 date operations).
   - **The compiled guest is cached, and checked.** It loads through
     wasmtime's unsafe deserialize, so a tampered or stale file would
     run as native code. The cache is keyed on the guest's sha256,
     wasmtime's version and a hash of the engine config, kept in sheaf's
     cache folder with 0600 permissions, and recompiled on any mismatch
     or deserialize error. Deserializing checks only the engine and
     version, not which `.wasm` the file came from (spike), so the
     guest's hash in the key is what catches a stale cache.
   - **A Cargo feature, `forms-js`, on by default,** in sheaf-app beside
     `plugins` (sheaf-app Cargo.toml:18), since both need wasmtime, and
     in sheaf-cli, which brings wasmtime and Cranelift into the CLI for
     the first time (it has only the OCR features, sheaf-cli
     Cargo.toml:12-16).
     - Without it scripts don't run, and the Rust AF path (proposal 12)
       still formats and checks values; `sheaf form fill` runs that path
       only.
     - A CI check like sheaf-image's (ci.yml:64-70) keeps wasmtime out
       of sheaf-doc and sheaf-ops.
     - Tests build the guest on first use under `target/formjs` (about
       2 minutes clean), and CI caches it.

## Proposals (accepted at kickoff)

4. **Fill first, scripts after, detection last.** The roadmap's order is
   fill, scripts, authoring, detection, data, flatten. The corpus says
   most forms need no scripts:
   - None of the 29 IRS forms has a field script. Their only scripts are
     three Adobe version checks per file (proposal 13).
   - Format scripts are needed just to display values in 10 of the 40
     files: every state form except Colorado. Only 3 calculate (GA, OH,
     VA), and only Georgia does real arithmetic.
   - So: groundwork and the page-tool fixes (slices 1–5), appearances and
     filling (6–14), flatten and data (15–17), scripts (18–22),
     authoring (23–26), detection (27–28), then the plugin API and docs
     (29).
   - Data comes before scripts because IRS forms need it and it doesn't
     need scripts. Once scripts land, an import recalculates.
5. **A page keeps its form through every page tool.**
   - Crop, watermark and Remove Header/Footer carry the page's fields
     into the derived copy (bug 1).
   - Insert Pages, Replace Pages and Combine add the incoming fields to
     `/AcroForm /Fields`, and merge what they need: `/DR` fonts (renamed
     on a clash), `/DA` and `/Q` (pushed down onto the fields where they
     differ), `/CO`, and document-level scripts (name-tree keys renamed
     on a clash) (bug 2).
   - Copying some of a form's pages copies only the widgets on those
     pages. Today a field's widgets on the pages left behind come along
     with a null `/P` (bug 2).
   - **Names that clash are renamed, never merged** (bug 3).
     - A clash on any node of the incoming tree, terminal or not,
       counts: every IRS form's root is `topmostSubform[0]`, with
       `Page1[0]` under it. The incoming form's fields then all go under
       a new parent field named for its file (`fw9.topmostSubform[0]…`,
       then `fw9_2`).
     - Nothing is grafted under an existing node, which would change the
       kids' inherited `/FT`, `/Ff`, `/DA` and `/Q`. Merging would link
       the two copies' values, which is the known complaint about
       Acrobat's merge.
     - The rename is decided when the edit runs and kept in it, so the
       names sheaf shows are the names it saves.
     - A renamed form's own scripts still name the old fields. When the
       incoming form has scripts, the notice says so and suggests
       flattening it first (Insert and Combine offer that; slice 15).
   - **Scripts from more than one source don't mix.** Document scripts
     share one global scope, so renaming name-tree keys doesn't separate
     them: GA 500 and OH IT 1040 both define `DS_Init`, `DS_Arrays` and
     `UFOOOOOxa`, from different Ultraforms versions. When more than one
     source in the result brings document or field scripts, scripts are
     off for that document by default, with a notice offering to flatten
     the incoming forms or keep only the first form's scripts.
   - **Duplicate Pages gives the copy its own widgets** (bug 4), renamed
     by the same rule, so the copy is a separate form. Acrobat may link
     them instead (to check; see Asks).
6. **A hybrid form loses its XFA copy on the first save that changes the
   form.**
   - 28 of the 29 IRS forms carry static XFA beside the AcroForm (all
     but 1040-ES); no state form does. Acrobat prefers the XFA copy, so
     after a fill of the AcroForm alone it shows stale or blank values
     (known behavior; not reproduced, since it needs Acrobat).
   - So when a value or the field tree changes (a fill, an import, a
     page tool that adds or removes fields), the save removes `/XFA`
     from `/AcroForm` and says so once: "Removed the form's XFA copy, so
     Acrobat shows the values filled here." iText's `removeXfaForm` and
     pdftk's `drop_xfa` do the same.
   - Removing it counts as removing content, so that save is a full
     rewrite (asking first on a signed file, proposal 7): XFA datasets
     can hold values Acrobat filled.
   - The binding isn't a name mapping:
     `topmostSubform[0].Page1[0].f1_01[0]` binds to
     `topmostSubform/f1_01`, and check boxes hold `0` or `1`. sheaf
     resolves it to read the datasets; updating them instead of removing
     them is left for later.
   - **Unless the datasets hold values the AcroForm lacks.** A static
     XFA form filled by an XFA-only tool can keep its values only in
     `<xfa:datasets>`; sheaf would show blanks, then delete the client's
     data on the first save. At open, dataset leaves are compared with
     `/V` by binding. Even a blank 1040 has 62 non-empty leaves, so "the
     datasets are empty" isn't a test. If they hold values the AcroForm
     lacks, a bar says "This form's XFA part holds values sheaf doesn't
     show", and dropping it asks first.
   - **Tooltips move to `/TU`.** The IRS XFA layers hold the forms'
     tooltips (4,977 `<speak>` elements, against 30 `/TU` entries) and
     366 scripts no other viewer runs. When the XFA goes, `<speak>` and
     `<toolTip>` text is copied into `/TU` wherever the binding
     resolves, so the Fields panel, the CSV's tooltip row and screen
     readers keep them.
7. **Usage rights go when the form changes; a replaced value forces a
   full rewrite; a signed file is never rewritten without asking.**
   - `/Perms /UR3` (Reader usage rights) is in 31 of the 40 files: every
     IRS form, NJ and PA. Its signature covers the original bytes, so a
     rewrite breaks it. Today a rewrite keeps it (bug 7), and Reader
     would then say the extended features are no longer available (from
     memory; untested).
   - So any save that changes the form, and any full rewrite, removes
     `/Perms /UR3`, and drops `/SigFlags` where no signature field needs
     it. In the corpus, SigFlags 2 is set on exactly those 31 files, and
     none has a signature field. A certification (`/Perms /DocMDP`) is
     detected and kept; only `/UR3` goes.
   - **A replaced value forces a full rewrite,** as removing anything
     does since M9 slice 21 (`Snapshot::removes_content`, model.rs:918)
     and as README's Save model row says (README.md:152). Firms reuse a
     filled form as a template, and an incremental save would keep the
     last client's values in the earlier revision. Filling an empty
     field stays incremental.
   - **So does the first change to a form whose earlier revisions hold
     values.** Files arrive with revisions (VA 760 has 22 `%%EOF`
     markers, every IRS form at least 3), and a template filled and cleared in
     Reader, which always appends, keeps the last client's values in
     them. When the form check (slice 1) finds earlier revisions whose
     field values differ from the current ones, the first save that
     changes the form is a full rewrite, with a notice.
   - **Signed and certified files:** on a file with any signed field or
     a certification, a save that would rewrite asks: "Rewrite (breaks
     2 signatures)" or "Append (earlier values stay in the file)".
     - That covers a removal, a replaced value, dropping XFA, Flatten
       Fields and deleting a field.
     - It also covers M9's page delete, which today rewrites a signed
       file and breaks its signatures without a word (`removes_content`
       has no signature check). ROADMAP.md:293-294 left asking first to
       M12; this pulls it forward for any rewrite of a signed file.
     - Signed fields are read-only, and moving or deleting one asks
       first.
     - Signed fields arriving through Insert or Combine are flattened to
       their appearance, or kept with a notice: "The signature from
       fw9.pdf is no longer valid here."
     - On an encrypted file, until M11, only Rewrite is offered, with
       the encryption notice (proposal 22): an incremental save of an
       encrypted file isn't possible yet (M11 bug 2).
     - Signing itself is M12.
   - **Every way out follows these rules.** They live in `build_rewrite`
     (save.rs:366) and the incremental writer, not in one save function:
     - Save, Save As and recovery sidecars, by both strategies: values
       kept, appearances made, `/XFA` and `/UR3` removed if the form
       changed.
     - Export Clean Copy (save.rs:33) keeps fields and values
       (README.md:240), under the same rules. M11's sanitize offers
       removing or flattening them.
     - Export Flattened Copy (save.rs:169) keeps fields unless "Form
       fields too" is on (proposal 18).
     - Extract Pages, Split (save.rs:66, :73) and the CLI's Combine
       follow the page-tool rules (proposal 5).
     - `print_pdf` (save.rs:132), and so the print dialog's Save as PDF,
       flattens (proposal 18).
     - Stamps made from a page, and the comment summary's page images,
       show the page's field values, unsaved ones included (slice 12).
     - One parametrized test runs every entry point on a filled hybrid
       1040, and the form check is clean on each (slice 15).
8. **The field tree and values live in `DocState`; the file stays
   standard.**
   - Read at open (`FileFacts`, `read_open`, file.rs:281, :399) and for
     inserted sources, with inheritance resolved: names, types, flags
     (`/Ff`), values (`/V`, `/DV`), `/DA`, `/Q`, `/MaxLen`, `/Opt`,
     `/TU`, actions (`/AA`, `/A`), and each widget's page, rect, flags,
     `/MK`, `/AS` and appearance states. Plus `/AcroForm`'s `/DR`, `/DA`,
     `/CO`, `/NeedAppearances`, `/SigFlags` and `/XFA`, and the catalog's
     `/Perms`.
   - **Read defensively.** The tree comes from untrusted files and is
     read for every file at open, so a cycle would hang or overflow on
     any file, not just forms.
     - A visited set on `/Kids` and `/Parent`; depth at most 32; caps on
       field and widget counts, on `/Opt` length, and on the `/MaxLen`
       used for layout (1,000); rects, sizes and colors finite and
       clamped.
     - Over a cap, the form reads as "damaged: not fillable", with a
       notice, and the file still opens.
     - FDF and XFDF `<fields>` get the same limits.
   - Kept in persistent `im` maps (`Send`), like marks, with the saved
     values beside them for dirty tracking. A field has a sheaf id,
     mapped to its source and object id; its full name is data. Widgets
     follow page ids, so moves and deletes carry them.
   - **Re-bound after a save.** A full rewrite renumbers every object,
     and `rebase_to_saved` (model.rs:970-1006) re-points only pages and
     resets the saved outline, marks and labels. M10 makes it also
     re-read the saved file's field tree, map sheaf's field ids to it by
     write order (the file was written from the model), not by name, and
     reset the saved values. Otherwise the next incremental save writes
     stale or duplicate objects, as pages did in M9 bug 13. Save As and
     undoing past a save go the same way.
   - Untouched fields' appearances, and keys sheaf doesn't read, stay in
     the source and are written back as they were.
   - **No `/SheafField` JSON.** Fields aren't sheaf's marks: the standard
     keys hold everything, Acrobat round trips stay simple, and M11's
     sanitize has nothing extra to strip.
   - Saving writes `/V` on the field, `/AS` on its widgets, and new
     appearances, by both strategies. The incremental writer writes only
     the changed field and widget objects (its `changed` map,
     incremental.rs:66-68), and recovery sidecars carry values the same
     way.
9. **One undo step per committed field.**
   - A commit is leaving a field (Tab, Enter, a click elsewhere), a
     click on a check box or radio button, or a choice picked. Typing
     inside a field isn't history; Esc reverts it.
   - The edit, `Edit::FieldsSet`, holds the committed value and every
     value calculations changed, resolved. Replay never runs a script,
     so history stays exact (M9 decision 16), even for a script that
     reads the clock. Values document scripts set as they start are held
     and join the first commit's edit; if focus leaves with no commit,
     they become a step of their own, "Form set 2 fields" (proposal 13).
   - Import, Clear Form and a Reset button are one step each, and so is
     a flatten. Authoring is one step per gesture ("Move 6 fields").
   - History reads "Fill “Line 1a” on page 1", "Fill “Line 1a” (and 3
     calculated fields)", "Fill “Name” (and 2 set by the form)", "Import
     form data (24 fields)", "Clear form".
   - **Pending commits.** A document's field events go through one
     queue, in order.
     - Any command that reads or writes the document (save, autosave,
       print, export, undo and redo, a History jump, page tools, close,
       plugin calls) first commits the focused field and waits for the
       queue to drain, up to the 1 s commit deadline.
     - A calculated value for the field being typed in waits until that
       field commits.
     - A rejection that lands after focus moved still restores the
       previous value.
   - **Ctrl+Z in a field** undoes the field's own typing, and reverts it
     as Esc does when there's nothing left; Ctrl+Y and Ctrl+Shift+Z
     redo (both are document Redo today, main.rs:497-498). None of them
     reaches document Undo or Redo. Today Ctrl+Z would undo the previous edit
     and orphan the typed text (bug 11).
10. **sheaf writes the appearance of every field it changes. It never
    sets `NeedAppearances`, and doesn't fill through PDFium.**
    - 91% of the corpus's text widgets (5,338 of 5,864) have no
      appearance until they're filled, and no file sets
      `NeedAppearances`. The generator is the core of filling.
    - `NeedAppearances` hands the job to each viewer, and a viewer that
      doesn't run format scripts (sheaf's own PDFium build among them)
      draws the raw `/V`, not the formatted value.
    - PDFium's form-filling calls (pdfium-render can set text and check
      box values) keep values in PDFium's own copy of the document,
      outside sheaf's model and history; they'd show raw values, and the
      result would have to be read back out of PDFium.
    - Fields sheaf didn't change keep their appearances.
    - A file that arrives with `NeedAppearances` (pdftk writes it with
      `need_appearances`, or for rich-text data) gets appearances for
      its valued fields on the first save that changes the form. The
      flag is cleared only when every one could be made.
    - **On screen,** a field sheaf changed is hidden in PDFium by its
      slot (`set_annots_hidden`, as comments are) and drawn from the
      appearance sheaf will save, rendered by PDFium. So the screen
      shows what the file will. While typing, sheaf's field editor draws
      it (proposal 11).
    - **Field pictures never touch the disk.** M9's turned tapes write a
      one-page PDF to the generated cache and a 600 px PNG beside it
      (stamp_preview.rs:18, :55-72, :113-123), and those outlive the
      document (generated.rs:1-5). For fields that would leave SSNs and
      amounts in plaintext under `~/.cache/sheaf`, against M11 proposal
      11. So a field's picture:
      - is rendered from bytes in memory (`PdfiumEngine::open_bytes`,
        sheaf-render lib.rs:255) at the tile's zoom, not a fixed 600 px;
      - is cached in memory for its document only, and dropped at close;
        never `generated::store`, and never a PNG;
      - is made off the UI thread, batched per page, so Ohio's 319-field
        calculation order isn't 319 PDFium opens.
      - Slice 6 tries whether re-rendering the page from its source plus
        an in-memory incremental section is cheaper than one picture per
        field.
      - A test fills, closes, and finds no new file in `SHEAF_CACHE_DIR`
        (the compiled guest aside).
    - **Tests check with form drawing off.** sheaf's screen draws a value
      that has no appearance, since PDFium's `FFLDraw` reads `/V` (bug
      10). So the pixel checks render appearances only, which is what
      other viewers see.
11. **Appearances use the field's own font; a bundled Unicode font
    covers the rest.**
    - The corpus is all simple single-byte fonts, Type 1 or TrueType,
      with no Type 0 fonts and no rich text. Encodings vary: 3,904
      fields use WinAnsi (IRS, NY, IL, Ohio's embedded TrueTypes); 1,806
      use Acrobat's default `/Helv`-style resources, a `/Differences`
      array in PDFDocEncoding's layout over the standard font's built-in
      encoding (10 of the 11 state forms); 79 (PA-40's Arial
      family) use MacRomanEncoding plus `/Differences`. 733 use
      ZapfDingbats' own encoding, and 114 name a font missing from
      `/DR`.

      | Fields | Font in `/DA` | In `/DR` |
      |---|---|---|
      | 2,942 | HelveticaLTStd-Bold or -Roman (IRS) | not embedded, with `/Widths` |
      | 110 | HelveticaLTStd-Bold (1040-ES) | missing |
      | 4 | ArialMT (1040-ES) | missing |
      | 1,251 | Helvetica | standard 14, no `/Widths` |
      | 733 | ZapfDingbats | standard 14 |
      | 498 | Courier-Bold | standard 14 |
      | 432 | CourierNew,Bold | embedded, whole font |
      | 358 | Arial | embedded, whole font |
      | 168 | TimesNewRomanPSMT | embedded, whole font |
      | 68 | OCRAStd | embedded, whole font |

    - Widths come from the font's `/Widths`, or, for the standard 14,
      from built-in AFM tables looked up by glyph name: Helvetica, Times
      and Courier in four faces each, Symbol and ZapfDingbats. sheaf has
      Helvetica and Helvetica-Bold widths for ASCII and some punctuation
      (stamps.rs:207-254); the full AFM tables, and the other 12 faces,
      are new.
    - Text is encoded in the field font's encoding: WinAnsi, MacRoman,
      or the built-in encoding with `/Differences`, each resolved by
      glyph name.
    - A font named in `/DA` but missing from `/DR` falls back by name
      (Helvetica, Arial and `ArialMT` to Helvetica, Times to Times,
      Courier to Courier), written as a non-embedded font.
    - Characters the field's font can't encode are drawn in a fallback
      font: Noto Sans, under the SIL OFL (kickoff), subset at
      save and embedded as Type 0 with a `ToUnicode` map. Nothing in the
      corpus needs it, but "?" in a client's name on a federal form
      isn't acceptable.
      - The OCR layer's Type 0 and CIDFontType2 dictionaries are a
        starting point (text_layer.rs:395-500). But it embeds one fixed
        glyphless font (every CID is glyph 1, `/DW` only, an identity
        `ToUnicode`), so subsetting, the CID-to-glyph map, `/W` widths
        and a per-glyph `ToUnicode` are new.
    - **Text beyond simple Latin.** Values are normalized to NFC at
      commit (macOS input arrives as NFD). `MaxLen` and comb cells count
      grapheme clusters, and a comb cell holds one cluster. Right-to-left
      text and complex shaping are out, with a notice. A character no
      bundled font covers (CJK, emoji) is refused at commit: "This field
      can't hold 王 in a way other viewers will show." sheaf never
      writes `?` or `.notdef`. Installed fonts come later (Not in M10).
    - **The editor's font.** The field editor (slice 11) paints with
      bundled faces whose widths match the field's: Liberation Sans,
      Serif and Mono (SIL OFL) for Helvetica and Arial, Times and
      Courier. It uses them for the characters the field's font encodes,
      and Noto Sans for exactly the characters the appearance will draw
      in the fallback. A field whose embedded font has no Liberation
      match (OCRAStd, 68 fields) is painted in that embedded font if
      GPUI can load it, else in Liberation Mono for a fixed-pitch font
      and Liberation Sans otherwise. So a typed value lines up with the
      appearance it saves as.
      `TextInput` can't: it paints one GPUI font and always aligns left
      (text_input.rs:545-548, :610), and 78% of the corpus's text
      widgets are right-aligned or centered.
    - New dependencies for subsetting, font metrics, normalization and
      grapheme clusters (for example `subsetter`, `ttf-parser`,
      `unicode-normalization` and `unicode-segmentation`; licenses to
      check).
    - This settles M9 decision 11 for forms. Stamps, headers and the
      comment summary can move to the same font later (Not in M10).

13. **Scripts get Acrobat's form objects, and nothing that reaches out.**
    - **In:** the AF functions; `event` (`value`, `rc`, `change`,
      `willCommit`, `target`, `selStart`, `selEnd`…); `this` as the
      document (`getField`, `numFields`, `getNthFieldName`, `resetForm`,
      `calculateNow`, `print`); Field values and properties (`display`,
      `readonly`, colors, `charLimit`, items, `setFocus`); `app.alert`,
      `beep` and `response`; `util.printf`, `printd`, `scand` and
      `printx`; `console.println`; `color` and `display`.
    - **Harmless no-ops,** never left undefined (an undefined method
      throws and stops the rest of the script): submitting and mailing,
      URLs and launching, data objects, importing and exporting data,
      `saveAs`, `closeDoc`, `app.quit`, setting `dirty`, opening
      documents, privileges, menus and toolbars, page templates
      (`spawn`), adding or removing fields and pages. Each one is
      logged. None touches sheaf's modified flag (Ohio's open action
      sets `dirty = false`).
    - **Never:** network, files, fullscreen (`app.fs`), password prompts
      (`app.response` with `bPassword` returns nothing), silent printing.
    - **What the guest sends back is untrusted.** Field ids are checked
      against the model; a value is at most 64 KiB and a list at most
      10,000 items; updates per event are capped, and the rest dropped
      and logged. pdf.js's page-num command is honored only during a
      user action; zoom and layout are ignored and logged.
    - **Dialogs** are sheaf's, titled with the document's name and
      saying they come from it. One per user action within 5 s, as
      pdf.js gates them (app.js:427-430), with "Don't show more from this
      document". `print` needs a user action and always opens the print
      dialog.
    - **Focus:** a script's `setFocus` is honored once per user action,
      so a validate that refocuses its field can't trap the user, and Esc
      always leaves.
    - **Timers** (`setTimeOut`, `setInterval`; pdf.js needs one for its
      activation window) are capped in number and interval, paused while
      the window is hidden, and stopped at close.
    - **`eval` stays on.** Georgia's and Ohio's generated libraries use
      it, and it can't leave the guest.
    - **Adobe's version checks never run.** Every IRS form has three
      `!ADBE::` document scripts. Depending on `app.viewerType` and
      `viewerVersion` they call `app.alert`, `app.response`,
      `app.launchURL`, `app.findComponent` or `getURL`; under the corpus
      run's stand-in (version 0) every IRS form reached `app.response()`
      on open. sheaf skips `!ADBE::*` scripts and sets
      `ADBE.Reader_Value_Asked` and `Viewer_Value_Asked`, as pdf.js
      does.
    - **When scripts run:** at open, the worker sets up the document's
      sandbox in the background (decision 3), and no form JavaScript runs.
      The document's own scripts start at the first interaction with one
      of its fields, with pdf.js's Open event, where document-level
      scripts run (7 ms for NY IT-201, 70 ms for GA 500, in the guest).
      Until then the stored appearances show.
      - Values the document scripts set as they start (Ohio's `DS_Init`
        sets `today` and `UPC_ScanDate`) are held and join that first
        commit's edit. If focus leaves with no commit, they become their
        own step, "Form set 2 fields" (proposal 9).
      - When a store is rebuilt (after a trap, or evicted), the model's
        values are pushed in and the scripts' start-up writes are
        dropped: the model is the source of truth.
      - `/OpenAction` JavaScript, page open and close actions, and
        document events (WillSave, DidSave, WillPrint, DidPrint) don't
        run in M10. They're logged.
    - **Triggers:** keystroke, validate, calculate and format; Focus,
      Blur, Mouse Down, Mouse Up, Enter and Exit (Ohio has 3 Mouse Down
      actions, Georgia 1 Exit).
    - **Order,** as Acrobat documents it and pdf.js and PDFium implement
      it: keystroke on each key; keystroke with `willCommit`; validate;
      the value commits; every field in `/CO` calculates, each running
      its own validate and format; then the field's format. Format
      changes only the appearance, and `/V` stays raw. A calculation
      that sets fields doesn't start another round. A value typed into a
      calculated field lasts until the next calculation, as in Acrobat.
    - **Where implementations differ,** sheaf does what the forms expect
      of Acrobat:
      - a rejected commit (`rc = false`) restores the previous value, as
        Acrobat's reference says and PDFium does (pdf.js clears the
        field);
      - validate may rewrite `event.value` (pdf.js; PDFium drops it). CA
        DE-4 and the I-9 depend on it;
      - a Calculate event starts with the field's current value (pdf.js
        starts it at `null`, and Ohio's scripts throw; proposal 12's
        patch);
      - `AFTime_Format` reads 24-hour values, and date and time
        keystrokes check the range (pdf.js does neither; proposal 12);
      - numbers round as `toFixed` does (pdf.js: 1.005 to two places is
        `1.00`; PDFium adds 1e-15 and gives `1.01`). Acrobat's own answer
        is in the Asks.
    - **Errors** name the field and trigger in a script log (Forms >
      Script Log…), and filling goes on.
    - **`[forms] scripts = false`** in `settings.toml` turns scripts off
      firm-wide; Forms > Run Scripts turns them off for one document, for
      the session, and "Don't show more from this document" lasts the
      session too. Nothing is kept by a client file's path. The Rust AF
      path still runs.
    - **Out of reach in M10:** Georgia's and Ohio's long tail (spawning
      page templates with renamed fields, `execDialog`, `buttonSetIcon`,
      a print barcode built through `eval`, moving fields at run time).
      Those forms still fill and print without them.

## Slice notes

1. Done. The form check is `sheaf_doc::forms::check`, built from the
   planning probe; fixtures and the corpus lookup sit beside it.
   - **`check(bytes, password)`** (and `check_file`) gives a `Report`:
     pages, terminal fields, widgets on pages and on page templates, the
     XFA copy's packets (and whether it's dynamic, `/NeedsRendering`),
     `NeedAppearances`, usage rights, a certification, `/SigFlags`,
     signature fields and how many are signed, revisions, and
     `findings`. Findings about fields or widgets name them, a widget by
     its field's full name:
     - widgets no field in `/Fields` reaches; widgets in the file on no
       page (not those on page templates, `/Names /Templates`, where
       forms that spawn pages keep them); on more than one page; whose
       `/P` is another page, or null or not in the file (a missing `/P`
       is fine);
     - fields whose `/Kids` hold a field or widget whose `/Parent` isn't
       them (another field, or none): pdf.js names fields up `/Parent`,
       PDFium follows `/Kids`, so the two see different fields;
     - fonts a `/DA` names (the widget's, its field's, or the form's)
       that `/DR /Font` lacks, counted by widget;
     - full names more than one terminal field has;
     - values with no appearance on the widgets a viewer draws (on a
       page and not Hidden; `NoView` ones still print): a text or choice
       value with a widget that has no `/AP /N`, or a check box or radio
       value no widget shows (`/AS` in that state, with an appearance
       for it);
     - values an earlier revision holds that the current one doesn't
       (replaced or cleared). A revision ends at a `%%EOF` after
       `startxref n`, for an `n` no earlier `%%EOF` gave, where lopdf
       reads the file up to it without rebuilding its cross-references
       and finds pages. So a `%%EOF` in a stream (an attached PDF), a
       trailer written twice and a linearized file's first-page section
       aren't revisions. The last 256 are read. (lopdf's strict mode
       would also catch a rebuilt cut, but it refuses things real files
       do.);
     - an XFA copy that doesn't fit: the template's fields as SOM paths
       (containers by name, or `#subform` and the like when unnamed; an
       exclusion group as one field; nothing hidden, no prototypes)
       against the AcroForm's full names, without their `[n]` and with
       `\.` read as a dot. Not for a dynamic form;
     - a signature (UR3, DocMDP, a signed field) whose `/ByteRange` isn't
       `[0 a b c]` around a hex string, ending where a revision ends;
     - `/SigFlags` 1 with no signature field, or 2 with nothing signed
       (no signed field, UR3 or DocMDP);
     - a damaged tree: a node reached twice, more than 32 deep, past
       100,000 nodes, a full name longer than 64 KiB, or full names
       adding up to more than 64 MiB. The walk doesn't follow it, and
       reads the rest.
   - **Bounded on files from the wild.** A parent's name is in each of
     its kids' names, so full names stop at 64 KiB each and 64 MiB in all
     (the corpus's longest `/T` is 1,608 bytes), and the XFA paths the
     same. Values are compared by a hash of their text, read once per
     object however many fields share it, not copied per field. A `/DA`
     over 1 KiB isn't read, and the names shown for widgets outside the
     tree stop at 256 bytes. One root with a 1 MB value (or name) and
     2,000 kids took 8.7 s and 3.9 GB before this, and takes 0.03 s and
     16 MB; a 1 MB XFA container name around 3,000 fields, 10.9 s and
     5.9 GB before, 0.01 s.

     The cause: pdfium-render's lock doesn't cover every call. 185 of
     the 467 functions its `thread_safe` wrapper binds take no lock,
     among them `FPDFDOC_InitFormFillEnvironment`, which every load
     makes (`PdfDocument::from_pdfium`), `FPDF_GetPageSizeByIndexF`, the
     text calls and `FPDFBitmap_FillRect`. So PDFium parsed on two
     threads at once. Its parser keeps its depth in a process global,
     `CPDF_SyntaxParser::s_CurrentRecursionDepth` (in `.bss`, not
     thread-local): `GetObjectBodyInternal` saves it, adds one, fails
     past 64, and puts the saved value back. Interleaved parses put back
     stale values and it drifts up. It read 63 after an 8-thread run,
     and from then on every load failed, from one thread too (73 of 73).
     A lock around loads alone isn't enough: loads under one still
     failed (285 of 292) while other threads sized pages and read text.

     held across every use of PDFium: each call into a `PdfiumEngine`, its
     load and its drop, and `render_appearances`. `pdfium()` is private
     now, so nothing reaches PDFium around it. Documents on different
     threads take turns a call into the engine at a time (a page's render
     or text, a page of a search). A render's drawing was already one
     PDFium call under pdfium-render's lock, so renders of different
     documents interleave as before. The two whole-document walks, page
     sizes and the outline, take the lock a page or a bookmark at a time.
     The lock is fair (parking_lot's `FairMutex`). With std's mutex a
     thread that locked again at once kept winning: a 20,000-page size
     walk took 20 s to over 400 s while another document rendered in a
     loop (0.15 s alone), and a document opening during a search waited up
     to 228 ms. With the fair lock the walk takes 0.9 to 2.1 s and the
     open 0.3 ms.

   - **A field or widget listed twice isn't damage; a cycle is.** The
     reader first treated anything reached twice as damage, as the check
     does, which made 12 SafeDocs files unfillable. None has a cycle: a
     field in `/Fields` twice, a kid in `/Fields` as well as under its
     parent, one widget twice in a `/Kids`, a kid under two parents. Now
     a node is read where it's first reached, and roots that are
     someone's kid are read last, so they get their parent's name. Only a
     field that's its own ancestor is damage. The check still reports
     sharing.
   - **So the work is bounded by entries, not only nodes.** A node is
     read once, but each list is looked through wherever it's reached, so
     fields that share one `/Kids` array cost its length each time. The
     walk that finds the roots that are kids counts every entry of
     `/Fields` and of the `/Kids` arrays it reaches, and past 200,000 the

     no signature field, and a save through lopdf would have lost the
     update.

     The cause, in lopdf 0.45.0's `Reader::resolve_xref_and_trailer`: it
     read an `/XRefStm` only inside the `/Prev` loop, so a file with no
     `/Prev` never had its stream read. It merged the stream after the
     previous section's table, and `Xref::merge` keeps the first entry,
     so that table's stale entries won. And it only read the newest
     trailer's (it took the key from `trailer`, not `prev_trailer`), so
     older sections' streams were left out: what broke the 9. ISO 32000
     reads each section's stream right after its table, before its
     `/Prev`.

     else in the lock moved. #598 reads each section's stream right after
